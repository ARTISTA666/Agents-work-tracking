## 问题详细描述

报错弹窗原文：

```
Invalid request body. (request id: 20260903092118269507833c955d568jCizetKc)
Turn execution failed provider=374fb4ad-b946-46a3-8c99-c754c6d8eb77
provider_code=invalid_request model=glm-5.3-flash
request=8757806a-fd94-416c-b307-cd2e70447934
reason=invalid_request status=400 retryable=false
```

特征：

- 只在一个已经很长的 agent 会话里出现（该会话累计 1022 条消息、487 组工具调用、53 个工具定义）；
- `retryable=false / canRetry=false`，ZCode 内置重试不覆盖 400，本轮直接中断；
- 用户手动重试时请求体几乎不变，因此反复撞同一面墙。

## 排查过程与证据链（Doubao）

### 1. 先排除外部因素：本地中转、梯子、密钥都不是原因

- 跨 9/1–9/3 的运行日志中同类 400 共 **17 次**，其中 **12 次发生在直连 `https://api.b.ai/v1` 时期、5 次发生在走本地重试中转时期**——直连也犯，与本地中转无关；本地中转对 400 的策略本就是「立即透传不重试」，符合设计。
- 同一把密钥当天成功数百次（`model.request.completed` 数百次），`GET /v1/models` 稳定 200 且包含该模型——密钥有效。
- 故障同一时段连发 3 个纯文本小请求，分别 3.1s / 7.3s / 2.6s 全部 200；本地重试中转 `READ_TIMEOUT=180s`，并成功传回过耗时 135s 的响应——梯子/节点与本地链路均未掐断。
- 成败两类请求的请求头键集合完全一致，排除请求头因素。

### 2. 关键突破：从完整模型 IO 中还原真实请求体，发现两套序列化结构

ZCode 在 `~/.zcode/cli/rollout/model-io-*.jsonl`（开启 modelIoFullRetention 后）落盘了每次请求的完整 body。本次失败请求 `8757806a` 与相邻成功请求 `1960de7e` 是**两套不同结构**：

| 维度 | 成功请求（标准适配路径，`bodySource` 为空） | 失败请求（`bodySource=ai_sdk_options`） |
| --- | --- | --- |
| 消息装载 | body 内 `messages=0`，消息在外部组装并做 **tail 裁剪** | body 内塞**全部 1022 条历史** |
| 请求体大小 | 约 **115 KB** | 约 **1,791 KB（约 1.8MB，约 15 倍）** |
| token 字段 | Anthropic 标准 `max_tokens=128000`、`thinking`、`system` 顶层 | 驼峰 `maxOutputTokens=96000`，**缺 `max_tokens`、无顶层 `system/thinking`** |
| tools 结构 | 数组（协议要求） | **53 键的 dict 对象** |
| 内容块命名 | `tool_use / tool_result / thinking` | AI SDK 内部名 `tool-call / tool-result / reasoning / text` |
| 其他 | 结构稳定、前缀一致 | 3 条 `role=system` 混进 messages；`providerOptions` 里内嵌了本属客户端配置的 baseURL/apiFormat |

即失败那几轮，ZCode 偶发地把 **Vercel AI SDK 的内部 options 中间对象，未经标准 Anthropic 序列化/裁剪就当成 HTTP body 发出**。

### 3. 对照实测：单点「不规范」上游都容忍，真正的杀手是「又大又冷又非标准」

经本地中转对 `api.b.ai` 的 `/v1/messages` 做控制变量实测：

- 缺 `max_tokens` → **200**；`tools` 传 dict 对象 → **200**；system 混进 messages → **200**。这些「不规范」点单独出现都被上游容忍，**「缺字段导致 400」被证伪**。
- 用 AI SDK 的 `tool-call/tool-result` 拼一个**最小**工具块 → **400，约 1.7s 快速返回**，上游原文比界面更具体：`{"type":"1214","message":"messages 参数非法。请检查文档。"}`（响应头带 `x-oneapi-request-id`，说明 `api.b.ai` 是 one-api/new-api 类聚合网关）。
- 把 1.8MB 真实失败 body **原样重放两次 → 都是 200，但分别耗时 135.5s、119.0s**（input 约 34,308、output 约 2,111，正常 `message_stop`）。
- 把同一 body 只保留尾部 20 / 60 条消息（仍保留 53 个工具定义与工具块结构）→ **均超过 150s 无响应**。说明拖慢的不是消息总条数，而是**工具定义 + 工具调用历史这类结构**。

### 4. 会话级统计：两条路径成败完全分化

对该会话 rollout 全量统计：

| 路径 | 请求数 | 失败数 | body 大小（中位） | 耗时 |
| --- | --- | --- | --- | --- |
| 标准适配路径 | 268 | **0（100% 成功）** | 115 KB | 中位约 35s |
| `ai_sdk_options` 全量路径 | 6 | **6（100% 失败）** | 约 1,772 KB | 挂起 100–130s 后 400 |

历史失败请求的耗时集中在约 60–100s（60.6 / 60.9 / 61.1 / 86.3 / 100.5s），与「后端处理不及、在网关时限处被中断」吻合。

### 5. 回应「是不是免费节点上下文窗口不够高」：不是，方向恰好相反

- ZCode 给该模型配置的窗口为 **`limit.context = 1,000,000`（100 万 token）、output 128,000**；界面「上下文不到 50%」对应的真实峰值是成功请求 `1960de7e` 的 **inputTokens=369,948（约 37 万，占 37%）**。
- **这个 37 万 token 的请求恰恰成功了**（其中 cacheReadTokens=369,280，output 276，耗时 206s）；而失败请求被上游实际识别的输入更小（重放仅计约 3.4 万 token）。若是「窗口装不下」，应当 token 越大越先失败，事实方向相反——**排除上下文容量不足**。
- 对 273 个带 usage 的成功请求统计：**缓存命中率中位数 99.8%、均值 90.6%**。标准路径每轮结构稳定、前缀一致，几乎全程命中 prompt cache，后端只需冷算极少量新 token，因此账面 37 万也能成功。
- 失败路径虽然也带了 `cache_control` 标记，但整体换成了另一套非标准结构，**与已缓存前缀对不上、缓存近乎作废**，只能对 1.8MB 全量冷算，还要网关把非标准块转换成后端认得的形态；免费渠道算力弱、有时限，60–100s 跑不完即被网关用一句笼统的 400「Invalid request body / messages 参数非法」退回。

## 根因结论（客户端 + 服务端双层叠加）

1. **客户端侧（ZCode）**：在超长工具型会话中偶发走 `ai_sdk_options` 这条「全量、不 tail 裁剪、非标准」的序列化路径（疑似 AI SDK 边界/回退行为），产出约 1.8MB、字段命名与结构都不标准的请求体，并使 prompt cache 失效。
2. **服务端侧（api.b.ai 免费聚合中转）**：对「缓存失效 + 全量冷算 + 非标准工具结构」的复杂请求处理极慢、后端渠道不稳，且**把处理超时/渠道转换失败笼统包装成 `400 invalid_request`**（更具体的内部文案是 type 1214「messages 参数非法」），具有很强误导性。
3. **放大因素**：ZCode 判定 400 `retryable=false` 不自动重试；用户手动重试发送的是同样巨大的 body，于是连续失败。

> 一句话：不是仓库门不够宽（窗口有 100 万、37 万都能过），而是这批货换了张分拣系统认不出的装箱单、提前备好的缓存货架用不上，免费人工在规定时间内没拆完，就把货退回并贴了「包裹不合格」。

## 解决方案与结果

- **采用**：对该会话执行 ZCode 的「压缩上下文（compact）」。压缩后历史变短、请求回到稳定的标准序列化路径、前缀重新稳定从而继续命中缓存，**问题随即消失，用户确认恢复正常**。
- **未采用但备选**：① 新开会话 / rewind；② 改走智谱官方通道（配置中已有的 Bigmodel `open.bigmodel.cn` 或 Z.ai `api.z.ai`），官方通道处理时限与算力更宽裕；③ **不建议对这种 400 加自动重试**——其本质是请求过大、后端需约 2 分钟，重试 5 次只会把等待放大数倍且未必成功。
- 全过程未改动代理（ClashX Meta TUN + 新加坡节点维持不变）、未改本地重试中转、未换密钥。

## 经验与复用顺序

1. **看到「Invalid request body」不要想当然认为是参数写错**：先拿到真实请求体（ZCode 可用 model-io rollout），再做「原样重放 + 控制变量对照」，以区分「必然的格式拒绝（快速 400）」与「超时被包装成 400（慢速、重放可能成功）」。
2. **判断是否上下文窗口问题，要看逐次 usage（inputTokens / cacheReadTokens）与成败方向，而非界面百分比**：若更大 token 的请求成功、更小的失败，即可排除容量问题。界面百分比 = 当前上下文 / 配置窗口（本例 37 万 / 100 万 = 37%）。
3. **prompt-cache 命中率是长会话稳定性的关键指标**：序列化结构稳定→前缀一致→缓存高命中→后端轻量；一旦序列化路径切换使缓存失效，就会退化为全量冷算，免费/弱后端极易超时。本例成功请求缓存命中率中位 99.8%。
4. **免费聚合中转（one-api/new-api 类）常把后端超时、渠道故障统一包装成 4xx**，排查时要拿到其更具体的内部错误码（本例 type 1214）和 `x-oneapi-*` 响应头，并结合耗时分布判断真伪。
5. **处置优先级**：压缩/重开会话（恢复稳定序列化路径与缓存）＞ 换官方通道 ＞ 盲目重试；对「输出前可重试、输出后只关连接」的中间件原则见上一篇 401 记录。
